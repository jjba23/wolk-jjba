* What lies here?

At its core, wolk-jjba is a server configuration built with Guix, treating the entire system as a programmable Lisp machine. It provides a range of functionalities, including:

- *Web Hosting*: Nginx serves multiple static websites, and acts as reverse proxy to custom applications.
- *Automatic HTTPS*: Certbot ensures all my websites get automatically generated and renewed HTTPS / SSL certificates with zero maintenance.
- *Gaming*: A Minecraft server (Forge with mods) for personal use.
- [[https://lucidplan.jointhefreeworld.org/projects][Lucidplan]] instance, my FOSS project management tool
- [[https://byggsteg.jointhefreeworld.org/][Byggsteg]] instance, my FOSS CI/CD tool that uses Lisp expressions (thunks) as CI pipelines
- [[https://wikimusic.jointhefreeworld.org/][WikiMusic]] instance, my FOSS musical knowledge wiki/knowledge base
- Automatic backup on cron basis and upload
- more...

* The Philosophy Behind Wolk-JJBA: Why Guix and Lisp?

My decision to build Wolk-JJBA as a Lisp machine powered by Guix stems from a desire for a computing environment that offers a unique blend of control, reproducibility, and expressiveness.

Guix: *Freedom and Reproducibility*. Guix's commitment to free software principles deeply resonates with me. Beyond that, its transactional upgrades and rollbacks provide a level of system stability and safety that is invaluable for a personal server.

The declarative configuration in Scheme allows me to precisely define my entire system state, making it reproducible and auditable. This eliminates the /configuration drift/ that  plagues other systems and this simplifies management significantly.

Guile Scheme: Power and Flexibility: Choosing Guile Scheme as the main language, offers immense power and flexibility. Lisp's inherent metaprogramming capabilities allow me to create highly tailored solutions that would be more cumbersome in other languages.

Building My Own Tools: Tailored Solutions: While adopting existing software is often practical, building my own allows me to create solutions that perfectly address my specific workflows and requirements.

This "build it yourself" approach, while requiring more upfront effort, ultimately leads to a more integrated and efficient computing environment. These tools are not just applications; they are *extensions of my Lisp machine philosophy*, allowing me to manage projects, automate tasks, and monitor my system in a way that aligns with my way of thinking.

The "Lisp Machine" Analogy: The term /Lisp machine/ isn't just a nostalgic reference. It reflects my aspiration to have a server environment where the underlying language (Lisp/Scheme) permeates various aspects of the system, from configuration to automation. This creates a cohesive and powerful ecosystem where tools can interact and build upon each other in elegant ways.

In essence, Wolk-JJBA is more than just a collection of server applications. It's an embodiment of my belief in the power of free software, the expressiveness of Lisp, and the value of crafting tools that are precisely tailored to individual needs.

I believe my approach provides me a level of understanding and control over my computing infrastructure that I find deeply satisfying and empowering.

* A new deployment

After installing Guix system on the VPS, we should reboot into the installation.

Then proceed to do a ~guix pull~ to update to the latest channels and Guix version. This should be done from a "regular" user account, not root.

Then, since I manage my VPS configuration from [[https://codeberg.org/jjba23/byggsteg][byggsteg]], I will create the needed dir, as root:

#+begin_src shell
mkdir -p /etc/byggsteg/job-clone/wolk-jjba
cd /etc/byggsteg/job-clone/wolk-jjba
guix shell git make
git clone https://codeberg.org/jjba23/wolk-jjba trunk
exit
#+end_src

Then as your "regular" user you will navigate again to the dir: ~cd /etc/byggsteg/job-clone/wolk-jjba/trunk~ and do a ~make sr~ to reconfigure the Guix system. Read below for some more info on this.

* Guix system

Your disk partitioning scheme surely will look different on a new install, so you should look at ~config.scm~  and at the auto-generated ~/etc/config.scm~ and change that.

It can be nice to disable in the ~config.scm~ the Nginx and Certbot services in the beginning.

#+begin_src scheme
;;(nginx-capability #:minimal-conf #t)
;;(certbot-capability)
#+end_src


Then activate firstly a minimal nginx to make the certs:

#+begin_src scheme
(nginx-capability #:minimal-conf #t)
(certbot-capability)
#+end_src

Then activate all services nginx:

#+begin_src scheme
(nginx-capability #:minimal-conf #f)
(certbot-capability)
#+end_src


Then we can reconfigure the system *as our normal user*!
#+begin_src shell
cd /etc/byggsteg/job-clone/wolk-jjba/trunk
guix shell git make
make sr
#+end_src

Some NGINX sites I use are protected behind basic auth. This works via a ~.htpasswd~ file, where I generate hashed passwords with ~openssl passwd~ and then add like:

#+begin_src shell
sudo htpasswd -c /srv/.htpasswd joe
#+end_src

This creates the file with:
#+begin_src
joe:$apr1$JmpYt3...$w28x...
sarah:$2y$10$vP...
#+end_src

After it's all complete reconfiguring the system, I reboot the machine and then configure Guix home for ~joe~, for convenience, it's not essential.

The encrypt / decrypt  cron-job commands come down to something like this:

#+begin_src shell
# To Encrypt
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000 -in my_backup.tar.gz -out my_backup.tar.gz.enc -pass file:$HOME/.backup-password
# To Decrypt
openssl enc -d -aes-256-cbc -salt -pbkdf2 -iter 100000 -in my_backup.tar.gz.enc -out my_backup.tar.gz -pass file:$HOME/.backup-password
#+end_src

** TODO: Fully automate Cleanup strategy for backups

Automate the implementation of  GFS (Grandfather Father Son) strategy, Most of my backups are done every 12 hours roughly.

See [[file:scripts/gfs-backup.scm]]

Given a 12-hour backup frequency:

- Son (Daily Retention): Keep all semi-daily backups for the last 7 days.

- Why: Gives you granular, 12-hour recovery points for recent mishaps.

- Father (Weekly Retention): Keep one backup per week (e.g., every Sunday at 22:45) for the last 4 weeks.

This allows you to roll back to weekly checkpoints over the last month.

Grandfather (Monthly Retention): Keep one backup per month (e.g., the 1st of the month) for the last 12 months (or indefinitely).

Also provides long-term historical archives for tax, compliance, or deep recovery needs.

* On Reproducibility: Why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
