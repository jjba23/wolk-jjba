* What lies here?

At its core, wolk-jjba is a server configuration built with Guix, treating the entire system as a programmable Lisp machine. It provides a range of functionalities, including:

- *Web Hosting*: Nginx serves multiple static websites, and acts as reverse proxy to custom applications.
- *Automatic HTTPS*: Certbot ensures all my websites get automatically generated and renewed HTTPS / SSL certificates with zero maintenance.
- *Gaming*: A Minecraft server (Forge with mods) for personal use.
- [[https://lucidplan.jointhefreeworld.org/projects][Lucidplan]] instance, my FOSS project management tool
- [[https://byggsteg.jointhefreeworld.org/][Byggsteg]] instance, my FOSS CI/CD tool that uses Lisp expressions (thunks) as CI pipelines
- [[https://wikimusic.jointhefreeworld.org/][WikiMusic]] instance, my FOSS musical knowledge wiki/knowledge base
- *Log Routing*: every syslog facility and every daemon writes to its own file, instead of one unreadable =/var/log/messages=.
- Automatic backup on cron basis and upload
- more...

* Repository layout

- =config.scm= :: the =operating-system= definition that ties every capability together.
- =home/joe.scm= :: the Guix Home environment for user =joe=.
- =src/wolk-jjba/= :: the system capabilities, one module per concern:
  - =prelude.scm= :: shared helpers and the Shepherd daemon factory.
  - =logging.scm= :: syslog routing for the Shepherd system log.
  - =nginx.scm=, =certbot.scm= :: web hosting and automatic HTTPS.
  - =crons.scm= :: mcron backup, upload and restart jobs.
  - =minecraft.scm=, =iptables.scm=, =packages.scm=, =maak.scm= :: the remaining capabilities.
- =scripts/gfs-backup.scm= :: Grandfather-Father-Son pruning for the storage box.
- =maak.scm= :: tasks (=make sr=, =make jr=, =make fr=, =make gfs-backup=).

* The Philosophy Behind Wolk-JJBA: Why Guix and Lisp?

My decision to build Wolk-JJBA as a Lisp machine powered by Guix stems from a desire for a computing environment that offers a unique blend of control, reproducibility, and expressiveness.

Guix: *Freedom and Reproducibility*. Guix's commitment to free software principles deeply resonates with me. Beyond that, its transactional upgrades and rollbacks provide a level of system stability and safety that is invaluable for a personal server.

The declarative configuration in Scheme allows me to precisely define my entire system state, making it reproducible and auditable. This eliminates the /configuration drift/ that  plagues other systems and this simplifies management significantly.

Guile Scheme: Power and Flexibility: Choosing Guile Scheme as the main language, offers immense power and flexibility. Lisp's inherent metaprogramming capabilities allow me to create highly tailored solutions that would be more cumbersome in other languages.

Building My Own Tools: Tailored Solutions: While adopting existing software is often practical, building my own allows me to create solutions that perfectly address my specific workflows and requirements.

This "build it yourself" approach, while requiring more upfront effort, ultimately leads to a more integrated and efficient computing environment. These tools are not just applications; they are *extensions of my Lisp machine philosophy*, allowing me to manage projects, automate tasks, and monitor my system in a way that aligns with my way of thinking.

The "Lisp Machine" Analogy: The term /Lisp machine/ isn't just a nostalgic reference. It reflects my aspiration to have a server environment where the underlying language (Lisp/Scheme) permeates various aspects of the system, from configuration to automation. This creates a cohesive and powerful ecosystem where tools can interact and build upon each other in elegant ways.

In essence, Wolk-JJBA is more than just a collection of server applications. It's an embodiment of my belief in the power of free software, the expressiveness of Lisp, and the value of crafting tools that are precisely tailored to individual needs.

I believe my approach provides me a level of understanding and control over my computing infrastructure that I find deeply satisfying and empowering.

* A new deployment

After installing Guix system on the VPS, we should reboot into the installation.

Then proceed to do a ~guix pull~ to update to the latest channels and Guix version. This should be done from a "regular" user account, not root.

Then, since I manage my VPS configuration from [[https://codeberg.org/jjba23/byggsteg][byggsteg]], I will create the needed dir, as root:

#+begin_src shell
mkdir -p /etc/byggsteg/job-clone/wolk-jjba
cd /etc/byggsteg/job-clone/wolk-jjba
guix shell git make
git clone https://codeberg.org/jjba23/wolk-jjba trunk
exit
#+end_src

Then as your "regular" user you will navigate again to the dir: ~cd /etc/byggsteg/job-clone/wolk-jjba/trunk~ and do a ~make sr~ to reconfigure the Guix system. Read below for some more info on this.

* Guix system

Your disk partitioning scheme surely will look different on a new install, so you should look at ~config.scm~  and at the auto-generated ~/etc/config.scm~ and change that.

It can be nice to disable in the ~config.scm~ the Nginx and Certbot services in the beginning.

#+begin_src scheme
;;(nginx-capability #:minimal-conf #t)
;;(certbot-capability)
#+end_src


Then activate firstly a minimal nginx to make the certs:

#+begin_src scheme
(nginx-capability #:minimal-conf #t)
(certbot-capability)
#+end_src

Then activate all services nginx:

#+begin_src scheme
(nginx-capability #:minimal-conf #f)
(certbot-capability)
#+end_src


Then we can reconfigure the system *as our normal user*!
#+begin_src shell
cd /etc/byggsteg/job-clone/wolk-jjba/trunk
guix shell git make
make sr
#+end_src

Some NGINX sites I use are protected behind basic auth. This works via a ~.htpasswd~ file, where I generate hashed passwords with ~openssl passwd~ and then add like:

#+begin_src shell
sudo htpasswd -c /srv/.htpasswd joe
#+end_src

This creates the file with:

#+end_src

* Logging, routing and retention

Logs used to all land in a single =/var/log/messages= file, which made the
file impossible to read or filter.  Since GNU Guix's =%base-services= run the
Shepherd's in-process system log, wolk-jjba now routes messages by syslog
facility and gives every supervised daemon its own file.

** How routing works

- The Shepherd's system log service (the =shepherd-system-log-service-type=
  documented in the Guix manual) reads everything daemons write to =/dev/log=
  and asks a =message-destination= procedure where to put each message.
- [[file:src/wolk-jjba/logging.scm][logging.scm]] replaces the default =message-destination= with
  =wolk-jjba-message-destination=, which dispatches on the message facility and
  priority.  It is applied to the whole service list by =system-log-capability=,
  which wraps the result of =%base-services= in =config.scm= with
  =modify-services=.
- [[file:src/wolk-jjba/prelude.scm][prelude.scm]] redirects the stdout/stderr of every
  =make-guile-server-shepherd-daemon= instance to its own file through the
  Shepherd's =#:log-file= constructor argument, so a chatty daemon never touches
  =/var/log/messages= at all.  The Minecraft and Icecast services do the same in
  [[file:src/wolk-jjba/minecraft.scm][minecraft.scm]] and =config.scm=.

** Log file map

| File                             | Contents                                                                |
|----------------------------------+-------------------------------------------------------------------------|
| =/var/log/messages=              | Catch-all: any unrouted facility, plus emergency/alert copies           |
| =/var/log/auth.log=              | Authentication and authorization (=sshd=, =sudo=, PAM, ...)             |
| =/var/log/mail.log=              | Mail subsystem                                                          |
| =/var/log/kern.log=              | Kernel messages                                                         |
| =/var/log/cron.log=              | Scheduled jobs (=mcron=)                                                |
| =/var/log/daemon.log=            | Daemons that log through syslog (for example =mpd=)                     |
| =/var/log/wolk-jjba/<service>.log= | stdout/stderr of each Shepherd daemon, one file per service           |
| =/var/log/nginx/=                | Web server access and error logs                                        |
| =/var/log/postgresql/=           | PostgreSQL                                                              |
| =/var/log/icecast/=              | Icecast's own logs                                                      |

Change the dispatch rules in [[file:src/wolk-jjba/logging.scm][logging.scm]]; change a daemon's log file by
passing =#:log-file= to =make-guile-server-shepherd-daemon=.

** Retention and rotation

Guix's =%base-services= also run the Shepherd's log rotation service.  It knows
about the files the system log creates and about the =#:log-file= files, so the
routed files are rotated (weekly, =zstd=-compressed, above a size threshold)
without any extra configuration.

#+begin_src shell
sudo herd status log-rotation     # next scheduled run
sudo herd files log-rotation      # files that will be rotated
sudo herd trigger log-rotation    # rotate now
#+end_src

** Observability

Grafana Alloy (see [[file:home/config.alloy][config.alloy]]) tails =/var/log/*.log=,
=/var/log/nginx/*.log=, =/var/log/messages= and =/var/log/wolk-jjba/*.log=,
attaches a =service= label derived from the file name, and pushes to Loki, so
the streams can be filtered per daemon in Grafana.  The noisy =Connection closed
by authenticating user root= line is dropped on the way.

* Useful tips

#+begin_src shell
# Follow a specific daemon's log after restarting it
sudo herd restart byggsteg-daemon && sudo tail -f /var/log/wolk-jjba/byggsteg-daemon.log

# Follow the routed system log, the web server or the database
sudo tail -f /var/log/messages /var/log/auth.log
sudo tail -f /var/log/nginx/error.log
sudo tail -n 300 /var/log/postgresql/pg_ctl.log
#+end_src

The system log files are created by the Shepherd as root.  I keep the
per-daemon directory and the system log files readable by my user (and by the
Podman Alloy container) with:

#+begin_src shell
sudo chmod 644 /var/log/*.log /var/log/messages
sudo chmod 755 /var/log/wolk-jjba
sudo chmod 644 /var/log/wolk-jjba/*.log
#+end_src

#+begin_src shell

#+end_src

* Backup retention and cleanup

Backups are made twice a day by mcron (see [[file:src/wolk-jjba/crons.scm][crons.scm]]) into =/wolk-jjba-backups/<project>/= and synced to the Hetzner storage box.

** Local retention

Each project has a make job and a matching clean job.  The clean job keeps only
the newest =N= archives:

| Project      | Keep |
|--------------+------|
| wikimusic    | 6    |
| byggsteg     | 6    |
| static-sites | 6    |
| lucidplan    | 6    |
| torikomi     | 6    |
| pingwing     | 6    |
| minecraft    | 3    |

** Remote retention

The upload job runs =rsync -av --delete=, so the storage box is an exact mirror
of the local, already-pruned tree.  The =--delete= is what stops the static-site
(and every other) backup from growing without bound: the old job used a plain
=rsync -av=, which left every pruned archive on the storage box forever.

** Optional long-term archives (GFS)

If you want weekly and monthly archives beyond the hot mirror, use
[[file:scripts/gfs-backup.scm][gfs-backup.scm]] (Grandfather-Father-Son).  It
runs as a dry run by default; pass =--apply= to actually delete expired
archives:

#+begin_src shell
make gfs-backup                            # dry run, prints the report
guile -L ./src ./scripts/gfs-backup.scm --apply
#+end_src

Keep long-term archives under a top-level =archive= directory, which the rsync
mirror excludes, so the two strategies never fight over the same files.

* On Reproducibility: Why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
