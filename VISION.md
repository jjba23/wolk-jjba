# Vision

wolk-jjba is a personal server written as a Guile program: one operating-system
record, nineteen modules under `src/wolk-jjba/`, a Shepherd service or timer behind
every promise, and `guix system reconfigure` as the only deployment tool. This
document is about what "the server is the program" should mean once the machine
matters enough that its owner's absence, a bad upgrade or a dead disk has to be
survivable — and about the handful of habits that would make it so.

## Where wolk-jjba is today

The tree is a 495-line `config.scm` beside nineteen modules under `src/wolk-jjba/`
— roughly 7,500 lines of Scheme — a 742-line `maak.scm`, and seventeen spec files
under `test/veritas/unit/`. `config.scm` is the only file that knows about every
capability; each module builds records, and each record ends up as a vhost, a
certificate, a firewall rule, a Shepherd daemon or a cron timer.

The edge is nginx with per-vhost HTTP/2 and HTTP/3, gzip, HSTS and a strict header
baseline, per-IP connection and rate limits, basic auth on the private vhosts, and
six applications behind it on loopback ports — Byggsteg, Lucidplan, WikiMusic,
Pingwing, Torikomi and Symbanta, plus the badge server that runs from its own
checkout. Certbot issues and renews over HTTP-01 and reloads nginx through a
deploy hook. PostgreSQL 16 holds what outgrew SQLite.

The rest of the machine is ordinary and specific: a Minecraft Forge server under
the Shepherd; MPD encoding one library into Icecast on three mounts at once (128
kbit/s Opus, 64 kbit/s Opus for mobile data, 96 kbit/s MP3 for reach) with the
music on a Hetzner Storage Box over CIFS and a five-minute health check that
restarts what it can and alerts on what it cannot; rootless Podman for two
accounts with the subuid ranges, cgroup delegation and a Docker-compatible socket
per account, and no container on the machine owned by root.

Backups are the most carefully written code in the repository. `jobs.scm` captures
a consistent input (`sqlite3 .backup` plus `PRAGMA quick_check`, `pg_dumpall
--clean --if-exists`), tars it, encrypts it with `openssl enc -aes-256-cbc -salt
-pbkdf2 -iter 100000` into a `.part` file renamed to `.enc` only once openssl has
exited successfully, writes a `.sha256` sidecar, and mirrors the lot to the
Storage Box hourly. `gfs.scm` rolls one archive per project per week and per month
into a long-term tree, because a mirror plus an hourly prune can only ever hold
the last day. The weekly auto-upgrade is deliberately still an mcron job: a
Shepherd timer that reconfigured the system could stop the timer that launched it.

Observability is five native Shepherd services — Prometheus, Loki, Tempo, Grafana
and Alloy — plus the node exporter, all on loopback, with provisioned data sources
and dashboards, alert rules by e-mail, and Alloy as the single OpenTelemetry entry
point. Their binaries come from pinned upstream releases with a version and a
SHA-256 each, in `monitoring-packages.scm`, because the Guix release this machine
runs packages none of them. `maintenance.scm` garbage-collects the Guix and Nix
stores, prunes images and caches, cleans `/tmp`, and publishes its own numbers as
metrics with alerts on them.

Security is two files and a habit. `iptables.scm` decides what a packet may do —
loopback first, then `hashlimit` and `connlimit` before any port accept, then a
default reject — and `sysctl.scm` decides how much work the kernel does before a
packet gets there. `security.scm` runs a daily audit, and `cve.scm` matches the
machine's packages against CISA's Known Exploited Vulnerabilities catalogue by
normalised word equality: deliberately coarse, so a package called `node` matches
every Node.js entry, and that false positive was chosen over the false
negative of a missed match.

Secrets have three copies and no fourth: a GPG file per secret under
`~/.config/wolk-jjba/secrets/`, the canonical plaintext in `/etc/secrets/` (root,
0600), and whatever derived file a program reads. `maak secrets` decrypts into a
pipe that goes straight into `ssh … install /dev/stdin`, so a plaintext is never
an argument, a history line or a process listing.

What constrains the future is that shape. `config.scm` reads four passwords from
`/etc/secrets` while it is evaluated, which is why a build needs those files to
exist and why the OS spec fabricates them; nothing is sealed to the host in git.
A capability is testable because it is a set of records, and the suites inspect
those records rather than a running machine — which is also why nothing proves
that the machine *boots*. Dashboards and alert rules are JSON and YAML copied by
`copy-file` lines in `monitoring.scm`: configuration in the repository, but not
derived from it. And the docs — one Org page per capability, HTML generated by
`scripts/export-docs.el`, never committed — are held to the code by the same
patch rule that holds the code to them.

## The vision

1. **The commit is the machine, and it can be booted somewhere else.** A scratch
   VM built from `config.scm` and the pinned channel boots the same vhosts, the
   same daemons and the same dashboards on localhost, so a change is tried before
   a reconfigure, and a bare-metal restore is a documented evening rather than an
   improvisation.

2. **Secrets are sealed to the host in the repository.** One encrypted file per
   secret, readable only by the machine it is for, replaces the GPG-to-ssh flow;
   evaluation still works in a test, rotation is one command, and a copy of the
   backup directory is worthless without that host's key.

3. **Every job can be rehearsed.** A restore is a timer that puts a sample archive
   back into a scratch tree and asserts what came out; the retention policy is run
   against a fixture; the firewall is diffed before it is applied. The backup path
   becomes the best-tested code in the tree instead of the least.

4. **Observability is derived, not copied.** A capability that declares itself
   gets its scrape job, its dashboard panels and its alert rules because it was
   declared, so a service added in March is monitored in March.

5. **The machine can say it no longer matches the commit.** A drift check compares
   what is running with the derivation of the checked-out revision and reports the
   difference as a metric, so "someone changed it by hand" is a fact with a
   timestamp.

## Features that are in scope and not built yet

- **Sealed secrets.** The three-copy flow works and is documented; what does not
  exist is anything in the repository. The hard part is that `config.scm` reads
  secrets at evaluation time, from a path, so a sealed store has to be materialised
  before the build without making an ordinary build require root.
- **A restore rehearsal.** `gfs.scm` is already pure enough to run its whole
  retention policy against an in-memory filesystem, and `veritas` already gives
  every suite a fixture directory; the hard part is restoring into a scratch tree
  and asserting a row count without touching live data or needing a second box.
- **Dashboards and alerts generated from records.** The panels are JSON and the
  rules are YAML, copied into the store. The hard part is generating them while
  preserving the ids, queries and thresholds that make an existing dashboard
  useful — and deciding whether Grafana's file format is an interface worth
  generating or a format worth owning.
- **A booted machine in CI.** `operating-system-spec` evaluates `config.scm` in a
  child Guile with one load path, which catches what does not evaluate; nothing
  catches what does not start. The hard part is a VM boot inside a test budget,
  and secrets at evaluation time inside it.

## New features that would be worth having

- **A reconfigure report.** Before `maak sr` applies anything, render what would
  change — services added and removed, vhosts gained and lost, timers rescheduled
  — into a short message. The records already know; nobody has asked them, and it
  is the cheapest guard against the reconfigure at two in the morning.
- **One machine-readable status document.** A JSON document naming every
  capability, its daemon, its port and its last-known health, so a phone or a
  script can ask the machine a question without a Grafana session. Not in scope.

## Contributions that would move the needle

1. **Build the restore rehearsal.** A backup nobody has restored is a hypothesis,
   and `gfs.scm`'s purity is the opening that makes the test cheap.
2. **Seal the secrets.** A day or two, and it removes the one thing in this machine
   that cannot be reproduced from a commit — the one thing that makes a rebuild an
   evening rather than an afternoon.
3. **A VM boot in CI.** A weekend, and it converts the spec suite from "it
   evaluates" to "it starts" — the difference that matters after an upgrade.
4. **Generate the dashboards.** A few days, and every future capability arrives
   monitored. Start with the alert rules; they are smaller and their absence is
   felt sooner.
5. **Version-aware CVE matching.** A week, and it turns a coarse audit into a short
   list a person can act on; the false positives are what make someone stop
   reading the mail.
6. **One troubleshooting entry per symptom.** Cheap, and it needs an operator's
   memory rather than a programmer's afternoon — the best possible first
   contribution from someone running this configuration on their own box.

## Compared to related projects

| Project | What it is | Where wolk-jjba differs |
| --- | --- | --- |
| NixOS configurations and starter frameworks (nix-starter-configs, digga, snowfall) | Declarative operating systems in the Nix language, usually with a flake, a module system and opinionated options for services. | The closest relatives: a machine as a value, atomically deployed. wolk-jjba is Guix plus Guile, one hand-written record rather than a framework's option modules, and its operations — backups, CVE audits, retention — are capability modules with records of their own rather than curated options. |
| Ansible, SaltStack | Agentless configuration management over SSH: YAML tasks applied to existing hosts, idempotent at the module level. | They manage machines that already exist and converge toward a described state; here the machine is a build output, so drift is not corrected but prevented — and the language is the same one the tests are written in. Neither wolk-jjba nor Ansible handles a fleet: this is one host. |
| MRSK (Kamal), Dokku, CapRover, Coolify | Deploy an application to a VPS over SSH, usually with containers, with rollbacks and a UI or CLI. | They give application-level ergonomics — one command per app, a history of releases — that wolk-jjba has only at the whole-system level. Here containers are for CI runners, every service is native, and a rollback is a Guix generation, not an image tag. |
| Docker Compose | A single-host multi-container stack described in YAML. | The same shape of problem solved by shipping images. wolk-jjba ships no images: a daemon is a Shepherd service, its files come from a pinned store, and its configuration is a gexp. |
| YunoHost, FreedomBox, Umbrel | Turnkey self-hosting distributions: an app catalogue, a UI, updates handled for you. | They are distributions and this is one person's machine, published as a worked example. They are far easier to begin with and far harder to read end to end — the trade this repository makes in the opposite direction. |
| sops-nix, agenix | Secrets sealed to host keys and committed to the repository, decrypted at activation. | The gap this project has: wolk-jjba keeps secrets out of git entirely and materialises them over SSH. Sealing them would remove the last manual step in a rebuild. |
| restic, borg, kopia | Deduplicating, authenticated, encrypted backup repositories with prune policies and frequent restores. | tar plus `openssl enc` plus a SHA-256 sidecar, with a hand-written GFS roll-up. The others bring deduplication, authenticated encryption and incremental restores; this one brings a policy that can be read in an afternoon and tested against an in-memory filesystem. |

What the others do that wolk-jjba could still add: sealed secrets with rotation
(sops-nix, agenix), authenticated backups whose restores are exercised (restic,
borg), fleet-level rollout and staged deploys (Ansible, MRSK), application-level
release ergonomics (Dokku, Coolify), and a boot-tested configuration as a matter
of course (NixOS CI). Where wolk-jjba is ahead and should stay ahead: one language
from the operating system to the shell wrapper to the test to the manual page, no
invented DSL between the intent and the record, a capability testable precisely
because it is a set of records, monitoring binaries pinned by hash, retention
local and off-site with checksums and a written restore path, secrets that never
touch a workstation disk, and an audit against the vulnerabilities that are
actually being exploited rather than a feed that merely exists.

## In the long run

The largest bet is that a configuration which can be booted elsewhere is worth
more than one that is merely reproducible: reproducible means the same derivation,
bootable means the same machine. Everything here leans on it — sealed secrets, a
rehearsed restore, a VM in CI — because they are the difference between a
repository that describes a server and one that can replace it.

The second bet is that operations should be rehearsable rather than runnable, in
the way code is tested rather than executed and hoped over. The third is that the
capability module is the right unit — one module, one record, one spec, one manual
page — and that the discipline is worth more than any framework's options. The
fourth, and the most external, is that the observability stack stops being
hand-pinned: either the packages land upstream or a channel carries them.

## Using this document

Two of these are worth starting now and neither is speculative: the restore
rehearsal, and sealing the secrets. The reconfigure report is the cheapest
improvement on the page. The rest would change what this repository is.

*This document describes intent, not commitments.*
